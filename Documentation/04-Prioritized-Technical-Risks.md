# Prioritized Technical Risks

Priority reflects impact on this console application's required behavior.

| Priority | Risk And Evidence                                                                                                                                                                                                                                                     | Consequence And Focused Response                                                                                                                                                                                                                                                                                                                                                                                         |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1 | **Gender update failure (scope resolved).** Historical probes and the user's manual checks returned 500. | D020 explicitly excludes Gender from editing and PATCH. Keep Gender read/filter/sort behavior; never include it in whole-person or selective update payloads. Final manual acceptance covers the five remaining editable fields. |
| 1        | **A rejected update can change data.** A 27-character surname returned HTTP 422 but was stored. The original full person response was restored and verified afterward.                                                                                                | Non-2xx does not establish rollback. Accepted D003: validate established constraints only, leave unknown rules to the server, and report uncertainty honestly without automatic retry, rollback, or extra recovery machinery. A normal user-requested read can inspect current state. The server's underlying cause remains unknown.                                                                                     |
| 2        | **Wrong session.** Official guidance requires the URL key on every request; live reads/writes used the same keyed URL. Lifetime is unknown.                                                                                                                           | Reads and edits can target different datasets. Acquire one scoped root and retain it for the workflow. Temporary data is accepted under D001; do not add cross-restart persistence machinery or treat the key as authentication.                                                                                                                                                                                         |
| 3        | **Search that appears successful but is ineffective.** `$search` returned HTTP 200 and all 20 people for both matching and nonmatching tokens. Unrestricted email/address lambdas returned HTTP 500, although scoped versions worked.                                 | Users may get misleading or failed results. Implement verified scalar `$filter` behavior first if approved; do not advertise unsupported fields or silently fall back to a different search meaning.                                                                                                                                                                                                                     |
| 4        | **Accepted risk of same-field overwrites.** People had neither a concurrency annotation nor observed ETags; no atomic mechanism was verified.                                                                                                                         | D008 accepts no conflict-prevention guarantee because it is not a justified current requirement. Do not add locking, pre-save rereads, or conflict machinery for that purpose. This scope decision does not prove the API lacks precondition support; revisit only if the requirement changes.                                                                                                                           |
| 5        | **Wrong record, stale key, or broadened filter.** Keys and strings use OData literals inside URIs. A unique UserName rename worked: the old URL became 404 and the new URL 200.                                                                                       | Track the actual current key after a verified rename; do not continue updating the old URL. Escape literals and encode URI values. Never use a list row number as the remote key. Duplicate keys and effects on relationships remain unverified.                                                                                                                                                                         |
| 6        | **False update outcome after a transport error.** A server can commit a PATCH before its response is lost; this path was not live-tested.                                                                                                                             | An automatic retry or confident failure message can mislead the user. Keep write retries explicit, report uncertainty, and use read-back for reconciliation without claiming it proves which actor made a change.                                                                                                                                                                                                        |
| 7        | **Response and boundary handling.** PATCH success returned empty 204 responses. A missing person returned GET 404 but PATCH 500. Validation returned 400 or 422; a declared enum member returned 500. Error codes were empty and JSON Content-Type parameters varied. | Do not deserialize 204, classify every 500 as missing/invalid input, or match exact English errors/Content-Type strings. MiddleName/Age null clearing and an Age above Int32 maximum worked; use the metadata's nullable Int64 type without inventing a business range.                                                                                                                                                  |
| 8        | **Unexpected provider response or misclassified live-test failures.** The user's tests and historical probes observed no continuation; `$top`/`$skip` with UserName ordering worked. The public sample is mutable and network-dependent. | D013 uses one collection GET with optional top/skip/orderby and no client paging behavior. D014/D015 accept one of five fields with ascending/descending; ordering beyond the tested UserName case remains unverified. Distinguish live failures in the default suite. Offset results can drift during mutations; nonunique fields can tie and no secondary key is automatically added. |

Do not claim restoration or add a recovery framework. Key collisions and relationships after renaming remain unverified. Concurrency capability remains unverified, with conflict prevention outside scope under D008.
