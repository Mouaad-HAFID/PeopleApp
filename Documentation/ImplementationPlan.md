This plan records the completed implementation of the accepted [decisions](decisions.md), using the [API evidence](02-Verified-API-Contract.md) and [requirements checklist](01-Requirements-Checklist.md). The five implementation steps are complete; the two-project structure is in place. The user confirmed fresh-session manual functional acceptance passed on 2026-10-25. The D019 cache-warning limitations remain as implemented and are accepted by the user as a non-blocking tradeoff.

**Scope resolution:** D005's match operations and case rules are accepted. On 2026-10-24 the user reported that all manual Gender updates returned 500 and explicitly removed Gender from the PATCH surface (D020). The editable fields are UserName, FirstName, LastName, MiddleName, and Age; Gender remains available for reads, filtering, and ordering. Remaining API acceptance checks stay user-owned; automated live tests are read-only.

1. **Create the foundation**
   - **Goal:** Establish the agreed buildable solution and test setup.
   - **Key tasks:** Create the .NET 10 console project under `src/PeopleApp` and xUnit v3 project under `tests/PeopleApp.Tests`, with the test project referencing the application. Use Spectre.Console 0.57, built-in HttpClient/System.Text.Json, and `ConsoleUi`/`Api` folder separation. Select compatible package pins and runner plumbing without adding production layers or frameworks.
   - **Verification:** Restore and build the solution; confirm xUnit discovery/execution is wired. Do not add dummy framework-behavior tests. All subsequent steps add application tests to this same project.

2. **Implement the session and read workflow**
   - **Goal:** List all people, select a current key, and display person details interactively.
   - **Key tasks:** Acquire and retain one keyed service root for the run; read People collections and single entities. Retrieve the collection with one GET; do not add page parameters or continuation-link handling. Support explicit result sizing through `$top` and `$skip` in Step 3. Display the complete entity body except top-level `@odata.context`, preserving other annotations, unknown/derived properties, arrays, nested values, and nulls. Handle empty results, GET 404, HTTP failures, transport/timeouts, and malformed responses.
   - **Verification:** Add controlled-response tests for session reuse, collection versus entity shapes, empty results, key-literal escaping, missing people, and full-response display. Add bounded GET-only live availability checks to the default suite now; require usable OData JSON, not fixed counts or a named fixture. Identify availability failures separately while failing the overall run; do not silently skip them.

3. **Add filtering, slicing, and ordering**
   - **Goal:** Refine the list while retaining the complete-list option.
   - **Key tasks:** Resolve D005 before fixing filter behavior. Support UserName/FirstName/LastName/Gender predicates with user-selectable AND/OR. Add optional `$top`, `$skip`, and one ascending/descending sort field from UserName/FirstName/LastName/Gender/Age. Send one collection request per list retrieval; do not add page parameters, continuation-link handling, implicit caps, secondary sort keys, raw expressions, `$search`, or collection filtering.
   - **Verification:** Test agreed matching/case behavior, enum literals, AND/OR, quote escaping and URI encoding, no matches, omitted/zero/invalid slicing inputs, all five sort selections/directions, and combinations of filters, slicing, and ordering in one request. Use controlled responses for deterministic tests. Confirm provider-specific ordering/query compatibility through manual read acceptance; only UserName ordering currently has live evidence.

4. **Implement selective person updates**
   - **Goal:** Edit the five accepted fields without sending unintended changes.
   - **Key tasks:** Support UserName/FirstName/LastName/MiddleName/Age; keep unchanged, replacement, and explicit null distinct. Allow null clearing only for LastName/MiddleName/Age. Validate established string/nullability constraints, nullable Int64 Age, and the declared 26-character surname limit, without inventing trimming, nonempty-name, or business-age rules. PATCH only intended fields; handle empty 204 and read back successful edits. Verify requested values before reporting success. After a verified key rename, use the new key. Exclude Gender from editing and PATCH.
   - **Verification:** Add controlled-request/response tests for each field, Int64 values beyond Int32, null clearing, omitted-field preservation, local rejection of established-invalid inputs, empty 204, and new-key routing. Cover 400/422/500, missing-person PATCH 500 versus GET 404, malformed errors, lost responses, and failed or mismatched read-back after an acknowledged PATCH. A failed write may have changed data: report uncertainty without automatic retry, rollback, conflict prevention, or a recovery subsystem. Test the editor's cancellation/confirmation and verify Gender is never sent.

5. **Complete end-to-end acceptance and handoff**
   - **Goal:** Verify the integrated interactive application against the agreed scope.
   - **Key tasks:** Review the browse/filter/select/details/edit/refresh/exit workflow and add any missing application-owned regression tests. Document run/test commands, selected dependencies, and current API limitations in the existing documentation. Incorporate supplied manual findings without rewriting historical probe outcomes.
   - **Verification:** Build and run the default suite, including live availability; distinguish provider/network failures from application failures. Perform user-owned manual acceptance in a fresh session: full and limited/ordered lists, one/multiple-field filters in both combination modes, no matches, complete details, all five editable fields, optional-field clearing, and post-rename lookup/read-back. Record before/after evidence and any test cleanup outcome; no automated mutation suite or further agent writes are authorized. Do not reuse the historical residual session as a clean fixture. Gender updates are excluded by D020, not claimed as supported.
